Arquiteturas de áudio: o que mora debaixo do cpal.

§ 01

Por que isso importa.

No Módulo 02 você usou cpal como se fosse mágica. Programa roda, áudio flui. Mas quando algo dá errado — xrun inesperado, latência que não baixa, dispositivo que não aparece — você precisa saber em que camada o problema mora.

Três exemplos concretos de quando esse conhecimento vira diferença prática:

  • Sua aplicação Rust funciona bem no notebook, mas no mini-PC que vai virar produto final trava toda vez que alguém abre o browser. Provavelmente é conflito de clock entre PipeWire e sua app — se você souber, resolve em 5 minutos configurando sample rate fixo.
  • Latência mínima que você consegue é 20ms por mais que diminua o block size. Provavelmente tem uma camada intermediária (PulseAudio emulation) adicionando buffer. Se você souber, pula essa camada indo direto no ALSA ou JACK.
  • Você quer que teu plugin apareça como source no OBS sem precisar de cabo virtual. Isso é uma feature do JACK/PipeWire, não do cpal. Sabendo, você usa a API certa.

Este módulo é o mapa. Quando terminar, você vai saber ler erros de áudio e escolher a camada certa pra cada problema.

Contexto: o que PortAudio resolve

Se você já usou PortAudio em C (ou via bindings Python/Go), entende a necessidade: cada sistema operacional tem APIs de áudio diferentes, e escrever o mesmo programa pra Windows/Mac/Linux sem abstração é reescrever 3 vezes. PortAudio é uma biblioteca C que uniformiza isso desde 1999. cpal em Rust é o equivalente moderno, com a mesma ideia: um callback, vários backends.

§ 02

A pilha do Linux.

No Linux, áudio atravessa várias camadas, do hardware até a tua aplicação. Cada camada faz uma coisa específica. Entender a pilha é entender por que tanta coisa diferente existe.

Sua aplicação Rust (cpal / pipewire-rs / jack-rs) onde você vive
PipeWire / JACK / PulseAudio servidores de áudio
ALSA (biblioteca userspace + ioctl) API padrão de áudio do Linux
Kernel (driver snd_* + subsistema ALSA) módulos do kernel
Hardware (chip de áudio, interface USB) o metal

O fluxo é de cima pra baixo quando você toca áudio, e de baixo pra cima quando grava. A camada de "servidores de áudio" é opcional no papel — você pode falar direto com ALSA — mas na prática todo sistema Linux moderno roda PipeWire ou PulseAudio, porque ALSA sozinha não permite múltiplas aplicações usarem o áudio ao mesmo tempo.

Por que tanta camada?

Historicamente o Linux teve várias soluções tentando resolver "múltiplos apps usando o áudio":

  • OSS (Open Sound System) — primeira tentativa, anos 90. Limitado.
  • ALSA (Advanced Linux Sound Architecture) — substituiu OSS, kernel 2.6 em diante. É a base hoje.
  • aRts, ESD — servidores de som antigos do KDE e GNOME. Mortos.
  • JACK (Jack Audio Connection Kit) — foco em pro-audio e baixa latência, mainstream desde ~2003. Ainda vivo.
  • PulseAudio — padrão desktop de 2008 a ~2022. Facilidade sobre performance.
  • PipeWire — unifica JACK + PulseAudio + ALSA num servidor só. Padrão atual.

No Arch moderno (e distros derivadas) você roda PipeWire com plugins que emulam PulseAudio e JACK simultaneamente. Qualquer app escrito pra qualquer um dos três funciona sem mudança. É um feito técnico notável.

§ 03

ALSA: o chão de fábrica.

ALSA é a API base de áudio do Linux. Vem duas partes:

  • Módulos de kernel (snd_usb_audio, snd_hda_intel, etc.) — drivers que conversam com o hardware
  • Biblioteca userspace (libasound) — API C que programas usam pra falar com os drivers

ALSA expõe dispositivos como arquivos em /dev/snd/:

terminalbash
ls /dev/snd/
# controlC0  pcmC0D0c  pcmC0D0p  seq  timer

# listar hardware
cat /proc/asound/cards
aplay -l
arecord -l

Cada interface de áudio vira um "card" com "devices" dentro. USB Scarlett vira card 1, built-in do notebook vira card 0, e assim por diante.

Quando falar direto com ALSA

  • Baixa latência extrema, pulando qualquer servidor de áudio
  • Sistema embarcado sem PipeWire/JACK rodando
  • Aplicações que precisam ter controle total do hardware (exclusive mode)

Problemas práticos de ALSA puro

  • Só uma aplicação por vez. Se Firefox tá tocando som, sua app não abre o dispositivo. (Tem o plugin dmix que resolve parcialmente, mas é limitado.)
  • Configuração por arquivo texto confuso. ~/.asoundrc tem sintaxe próprio, documentação obscura.
  • Sem conceito de "patching" entre apps. Não dá pra pegar a saída de um app e mandar pra entrada de outro.

Por isso, 99% das aplicações de áudio no Linux moderno passam por JACK ou PipeWire acima do ALSA.

§ 04

JACK: o servidor pro-audio.

JACK nasceu em 2002 com uma missão clara: baixa latência determinística e capacidade de "patchear" áudio entre aplicações como se fosse um mixer virtual.

O que JACK te dá

  • Clock único pra todas as apps. Todas tocam no mesmo sample rate, no mesmo block size, sincronizadas sample-accurate.
  • Patching visual. Ferramentas como qjackctl, patchage, qpwgraph deixam você ligar saída de uma app na entrada de outra arrastando fios.
  • Baixa latência previsível. Block sizes de 32, 64, 128 samples são normais.
  • Protocolo aberto. Documentado, estável desde 2005.

Anatomia de um JACK client

Uma aplicação JACK chama-se client. Ela se conecta ao JACK server (daemon separado) e recebe:

  • Um callback chamado a cada bloco (mesmo conceito do cpal, mas mais rígido com as regras)
  • Portas de entrada e saída virtuais, que podem ser conectadas a outras portas na rede JACK
conceito visualdiagrama
[ Microfone físico ] → ALSA → JACK "system:capture_1"
                                        │
                                        ↓ (você conecta)
                              [ Sua app JACK ]
                              porta_in → processa → porta_out
                                                      │
                                                      ↓ (você conecta)
                                          JACK "system:playback_1" → ALSA → [ Fone ]

Isso é poderoso. Você pode ter sua app Rust + Ardour (DAW) + OBS + Carla (host de plugins) todos rodando simultaneamente, patchados entre si, compartilhando o mesmo clock. Ferramenta fundamental pra produção de áudio no Linux.

Se você já usou JACK

Provavelmente com qjackctl. A interface velha mas funcional pra configurar sample rate, block size, iniciar/parar o daemon e ver status. Hoje no PipeWire você nem precisa mais — o daemon já tá rodando, e você só usa qpwgraph pra patching.

§ 05

PipeWire: o sucessor.

PipeWire apareceu em 2017 com uma ideia ambiciosa: substituir PulseAudio e JACK ao mesmo tempo, com um servidor só. Desde 2021-2022 é o padrão das principais distribuições (Fedora, Ubuntu 22.10+, Arch).

O que o PipeWire entrega

  • Compatibilidade com PulseAudio. Apps escritos pra PulseAudio (Firefox, Spotify, Discord) funcionam sem mudança.
  • Compatibilidade com JACK. Apps escritos pra JACK (Ardour, Carla, REAPER via Wine) funcionam sem mudança.
  • API nativa própria. Performance melhor que os dois modos de compat.
  • Roteamento unificado. Patching no qpwgraph ou helvum, com apps PulseAudio e JACK aparecendo no mesmo grafo.
  • Sessão por usuário. Não precisa ser root, não precisa iniciar daemon manualmente. Systemd user unit cuida de tudo.
  • Áudio e vídeo. PipeWire também lida com captura de webcam e screencast — antes eram sistemas separados.

Checando seu PipeWire

terminalbash
# Versão instalada
pipewire --version

# Módulos carregados (deve ter pulse e jack pra compat)
pw-cli ls Module | grep -E "pulse|jack"

# Sample rate e block size atuais
pw-metadata -n settings

# Listar todos os dispositivos e nodes
pw-cli ls Node

Ajustando pra baixa latência

Por padrão PipeWire usa block size de 1024 samples (21ms @ 48kHz) — bom pra navegação. Pra áudio pro, você quer 128 ou 64. Configuração persistente em ~/.config/pipewire/pipewire.conf.d/10-low-latency.conf:

~/.config/pipewire/pipewire.conf.d/10-low-latency.confconf
context.properties = {
    default.clock.rate          = 48000
    default.clock.allowed-rates = [ 44100 48000 96000 ]
    default.clock.quantum       = 128
    default.clock.min-quantum   = 32
    default.clock.max-quantum   = 512
}

Restart do serviço:

terminalbash
systemctl --user restart pipewire pipewire-pulse wireplumber
Cuidado com a configuração persistente

Quantum muito baixo (32, 48) cobra muito da CPU e pode causar xruns sistêmicos — não só na tua app, mas em Firefox, Discord, tudo que tá tocando áudio. Pra desenvolvimento, configure só quando for testar e volte ao normal depois.

§ 06

PortAudio: a ponte cross-platform.

PortAudio é uma biblioteca C criada em 1999 pra resolver o problema: "como escrever um programa de áudio que rode em Windows, Mac e Linux sem reescrever 3 vezes?". Ela abstrai as APIs nativas de cada sistema atrás de uma interface única.

Como PortAudio funciona

Você escreve um callback em C. PortAudio garante que o callback é chamado:

  • Via WASAPI, ASIO, WDM/KS ou DirectSound no Windows
  • Via CoreAudio no macOS
  • Via ALSA, JACK ou OSS no Linux

Mesma assinatura de callback, mesmo padrão de código, três sistemas. Foi revolucionário na época e ainda é muito usado. Muitas aplicações bem conhecidas usam PortAudio por baixo — Audacity, por exemplo.

Se você já usou PortAudio

Parabéns — você já tem 80% do modelo mental do cpal. A diferença é que cpal é Rust idiomático (ownership explícito, error handling com Result), não C com callbacks por ponteiro. A filosofia é idêntica: "um callback, vários backends escolhidos em tempo de execução."

PortAudio ainda faz sentido hoje?

Em Rust, cpal é a escolha natural. Em C/C++, PortAudio segue relevante, especialmente pra projetos que precisam rodar em sistemas antigos ou embarcados onde cpal não compila. Se você mantém código legado em Go, C ou Python, vai continuar vendo PortAudio bastante.

Comparação direta:

AspectoPortAudio (C)cpal (Rust)
Lançamento19992016
Cross-platformWin/Mac/LinuxWin/Mac/Linux/Web/Android/iOS
Backends LinuxALSA, JACK, OSSALSA, JACK (via feature)
APICallbacks C, ponteirosClosures Rust, ownership
Gestão de erroCódigos de retornoResult/Error
PopularidadeMassiva em C/C++Crescente em Rust
§ 07

Windows e macOS, brevemente.

Foco do módulo é Linux, mas vale saber o essencial das outras plataformas pra quando teu produto for distribuído.

Windows

  • WASAPI (Windows Audio Session API) — API padrão desde Vista. Razoável latência em exclusive mode (~5-10ms).
  • ASIO (Audio Stream Input/Output) — API da Steinberg, baixíssima latência (< 3ms). Driver por fabricante (Focusrite ASIO, RME ASIO). Licenciamento restritivo — pra incluir no teu produto precisa SDK.
  • WDM/KS (Kernel Streaming) — mais direto ao driver. Performance boa, API complicada.
  • DirectSound, MME — APIs antigas, ainda suportadas por compatibilidade. Latência ruim. Não use.

cpal no Windows usa WASAPI por padrão. ASIO exige feature flag e o ASIO SDK da Steinberg baixado separadamente.

macOS

  • CoreAudio — a melhor stack de áudio comercial. Latência consistente, API bem desenhada, uma única coisa pra aprender.
  • Audio Units (AU) — formato de plugin específico do macOS.

cpal no macOS usa CoreAudio. Nada pra configurar na maioria dos casos — "funciona e ponto". Desenvolvedores de áudio adoram macOS por isso.

Pro teu projeto

Desenvolvimento no Linux (PipeWire), distribuição pra Windows (WASAPI via cpal) e macOS (CoreAudio via cpal) é caminho viável. Os três sistemas hoje entregam latência razoável pra live streaming. Se um dia quiser competir em baixa latência extrema, aí entra ASIO no Windows e JACK direto no Linux.

§ 08

Onde o cpal se encaixa.

Agora a visão completa. cpal é uma camada de abstração Rust que roda em cima das APIs nativas:

Sua aplicação Rust callback + lógica
cpal (Cross-Platform Audio Library) abstração Rust
ALSA (Linux) | CoreAudio (macOS) | WASAPI (Windows) APIs nativas do SO
Kernel + Driver + Hardware o metal

Por padrão, cpal no Linux usa ALSA direto. Mas num sistema com PipeWire rodando, ALSA fala com PipeWire automaticamente (via plugin pcm_pipewire), então tua app cpal se comporta como client PipeWire sem saber.

Feature flags do cpal

Você pode ativar backends opcionais via Cargo:

Cargo.tomltoml
[dependencies]
# cpal padrão (usa o default do sistema)
cpal = "0.15"

# cpal com JACK explícito (Linux)
cpal = { version = "0.15", features = ["jack"] }

# cpal com ASIO (Windows, precisa ASIO SDK)
cpal = { version = "0.15", features = ["asio"] }

No código, você seleciona o host:

selecionando backendrust
use cpal::traits::HostTrait;
use cpal::HostId;

// Lista todos os hosts disponíveis no sistema
let available = cpal::available_hosts();
println!("{:?}", available);
// Linux típico: [Alsa, Jack]

// Força usar JACK em vez do default
let jack_host = cpal::host_from_id(HostId::Jack)?;
let device = jack_host.default_input_device().unwrap();
§ 09

Rust direto em JACK e PipeWire.

Quando cpal não é suficiente, você pode ir direto na API. Isso vale quando você precisa de recursos específicos — patching programático, transport control no JACK, nodes customizados no PipeWire.

Trilha JACK: crate jack

A crate jack é o binding Rust pra libjack. API bem próxima do C original, mas com tipos Rust.

Cargo.tomltoml
[dependencies]
jack = "0.13"
src/main.rs — JACK passthroughrust
use jack::{Client, ClientOptions, ClosureProcessHandler,
           Control, ProcessScope, AudioIn, AudioOut};

fn main() -> Result<(), Box<dyn std::error::Error>> {
    // Conecta ao JACK server
    let (client, _status) = Client::new(
        "rust-passthrough",
        ClientOptions::NO_START_SERVER,
    )?;

    println!("Sample rate: {}", client.sample_rate());
    println!("Buffer size: {}", client.buffer_size());

    // Cria portas de entrada e saída
    let in_port = client.register_port("in_1", AudioIn::default())?;
    let mut out_port = client.register_port("out_1", AudioOut::default())?;

    // Callback
    let process = move |_: &Client, ps: &ProcessScope| -> Control {
        let in_slice = in_port.as_slice(ps);
        let out_slice = out_port.as_mut_slice(ps);

        for (i, o) in in_slice.iter().zip(out_slice.iter_mut()) {
            *o = *i * 0.5; // passthrough com -6dB
        }
        Control::Continue
    };

    let active_client = client.activate_async(
        (),
        ClosureProcessHandler::new(process),
    )?;

    println!("Rodando. Conecte 'rust-passthrough:in_1' a algo via qpwgraph.");
    std::thread::park();

    active_client.deactivate()?;
    Ok(())
}

Rode com cargo run --release. Abra qpwgraph e você vai ver "rust-passthrough" com portas in_1 e out_1 patchable. Conecta a saída do sistema na entrada do teu app, e a saída do teu app no sistema — áudio flui.

Trilha PipeWire: crate pipewire-rs

A crate pipewire é o binding oficial Rust. API mais baixo nível que a do JACK, mais poderosa, mas mais verbosa.

Cargo.tomltoml
[dependencies]
pipewire = "0.8"
src/main.rs — listar nodes do PipeWirerust
use pipewire::{main_loop::MainLoop, context::Context};

fn main() -> Result<(), Box<dyn std::error::Error>> {
    pipewire::init();

    let main_loop = MainLoop::new(None)?;
    let context = Context::new(&main_loop)?;
    let core = context.connect(None)?;
    let registry = core.get_registry()?;

    let _listener = registry
        .add_listener_local()
        .global(|global| {
            println!(
                "id={} type={} version={}",
                global.id,
                global.type_,
                global.version,
            );
        })
        .register();

    main_loop.run();
    Ok(())
}

Esse exemplo lista todos os nodes do PipeWire rodando no sistema — sources, sinks, apps conectados. É o ponto de entrada pra qualquer coisa mais avançada: criar filter-nodes customizados, criar source virtual que seu app expõe como "microfone" pra outros apps, etc.

Quando usar JACK direto vs PipeWire direto vs cpal

cpal: a maior parte do tempo. Cross-platform, simples, suficiente. JACK: quando você quer teu app patchável com outros, visível no qpwgraph, e ainda ser Linux-compatível com sistemas que rodam JACK nativo (sem PipeWire). PipeWire direto: quando você precisa criar virtual devices, filter-nodes, ou qualquer coisa específica do ecossistema PipeWire.

§ 10
Experimento prático

Mesmo app, três backends.

Objetivo: rodar o passthrough do Módulo 02 com três configurações diferentes e medir a latência de cada. Sente na pele a diferença entre as camadas.

Configuração A — cpal default (ALSA via PipeWire)

É o que você já tem. Anote a latência medida no experimento do Módulo 02.

Configuração B — cpal com feature JACK explícita

Adicione a feature no Cargo.toml do teu projeto do Módulo 02:

Cargo.tomltoml
[dependencies]
cpal = { version = "0.15", features = ["jack"] }

E modifique o início do main() pra forçar host JACK:

mudança no main()rust
let host = cpal::host_from_id(cpal::HostId::Jack)?;
// resto do código igual

Rode e meça a latência. Compare com a Configuração A. Deve ser similar no Arch moderno (PipeWire fornece os dois backends), mas em Ubuntu padrão ou outras distros a diferença pode ser grande.

Configuração C — JACK direto (crate jack)

Use o exemplo do passthrough JACK direto da Seção 9. Compile, rode, meça latência com o cabo loopback.

Tabela de resultados

Anote os valores encontrados. Algo assim:

BackendLatência round-tripObservações
A. cpal default__ msquantum do PipeWire: __
B. cpal + feature jack__ msvia JACK emulation

Em teoria, as três deveriam dar latências parecidas no PipeWire moderno — ele unifica tudo bem. Se houver diferenças grandes, algum ajuste está diferente (sample rate, quantum, exclusive mode). Isso é aprendizado: você está sentindo na prática onde a latência mora.

O que você aprendeu ao fazer isso

Agora você sente a stack. Sabe que cpal é abstração, não mágica. Sabe trocar entre ALSA, JACK e PipeWire conforme a necessidade. E quando teu código der problema de latência no futuro, você tem o mapa mental pra debugar em qual camada olhar primeiro.

Glossário
ALSA
Advanced Linux Sound Architecture. API base de áudio do Linux, kernel + biblioteca userspace.
JACK
Jack Audio Connection Kit. Servidor de áudio focado em baixa latência e patching entre aplicações.
PulseAudio
Servidor de áudio desktop padrão de 2008 a ~2022. Facilidade sobre performance. Substituído por PipeWire.
PipeWire
Servidor moderno que substitui PulseAudio + JACK num produto só. Padrão atual nas principais distros Linux.
WASAPI
Windows Audio Session API. API padrão de áudio no Windows desde Vista.
ASIO
Audio Stream Input/Output. API da Steinberg, baixíssima latência, exige driver específico do fabricante.
CoreAudio
Stack de áudio do macOS. Bem desenhada, latência boa por default, usada também em iOS.
PortAudio
Biblioteca C cross-platform, precursora conceitual do cpal. Presente desde 1999.
NODE (PipeWire)
Unidade fundamental do PipeWire. Um node pode ser source, sink, ou filter. Aplicações criam nodes.
CLIENT (JACK)
Aplicação conectada ao JACK server. Tem portas que podem ser patchadas.
QUANTUM (PipeWire)
Block size do PipeWire. Padrão 1024, baixo pra pro-audio: 128 ou 256.
qpwgraph / helvum
Ferramentas gráficas pra patching visual no PipeWire. Substituem o qjackctl do mundo JACK.
FEATURE FLAG (Cargo)
Mecanismo de Cargo pra ativar funcionalidades opcionais em crates. No cpal: jack, asio.
