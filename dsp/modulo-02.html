Módulo 02 — Tempo real

O bloco e o callback: como o áudio chega no teu código.

No módulo anterior você gerou áudio e salvou em arquivo. Agora o áudio entra em tempo real pela interface, passa pelo teu código, e sai pela mesma interface. É onde "processar áudio" vira concreto — e onde a maioria dos projetos morre se ignorar as regras.

§ 01

Processamento ao vivo é outro mundo.

No Módulo 01 você gerou áudio e salvou em arquivo. Tranquilo: se o código demorasse 30 segundos pra gerar 2 segundos de áudio, ninguém percebia. O arquivo saiu certo.

Agora você quer processar áudio ao vivo: microfone entra na interface, o som da tua voz passa pelo teu código Rust, e sai imediatamente no fone. Isso muda tudo.

A nova regra é: se teu código demora um microssegundo a mais do que o orçamento disponível, o áudio glitcha. Click. Pop. Silêncio. O pastor vai ouvir. A live vai falhar. A conversa acaba.

Esse orçamento apertado é a constraint mais importante de áudio em tempo real. Tudo nesse módulo existe pra você entender e respeitar esse orçamento.

Atalho mental

Processar arquivo = correr maratona. Você tem tempo, só não pode parar. Processar ao vivo = dança de tango. Cada passo tem tempo exato pra acontecer. Atrasar um passo derruba o baile inteiro.

§ 02

O audio callback.

Quando você conecta a interface USB e o programa abre acesso ao áudio, o sistema operacional (ou o driver da interface) faz um acordo com teu programa:

"Eu vou te chamar repetidamente, em intervalos precisos. Cada vez que te chamar, vou te entregar um pedacinho de áudio que acabou de chegar e vou precisar que você me devolva outro pedacinho pra mandar pra saída. Essa chamada tem que durar menos que X microssegundos. Se você demorar mais, eu não vou te esperar — eu vou mandar silêncio ou o buffer antigo pra saída, e quem tá ouvindo vai perceber."

Essa função que o sistema chama repetidamente é o audio callback. É o coração de todo software de áudio em tempo real. E é uma função que roda sob regras especiais.

Fluxo do audio callback. Sistema entrega N amostras de entrada, espera N amostras de saída, dentro de um tempo fixo.

Como seu código parece em Rust (simplificado)

estrutura conceitualrust
// Isto é chamado pelo sistema, repetidamente, em intervalos fixos
fn audio_callback(input: &[f32], output: &mut [f32]) {
    // 1. Ler amostras de entrada
    // 2. Processar (filtros, ganho, etc.)
    // 3. Escrever amostras de saída
    for i in 0..input.len() {
        output[i] = input[i] * 0.5; // exemplo: ganho de -6dB
    }
}
§ 03

Block size: o compromisso.

Toda vez que o sistema chama teu callback, ele te entrega N amostras de cada vez, não uma por uma. Esse N é o block size (também chamado buffer size, period size, frames per buffer — é tudo a mesma coisa).

Por que em blocos e não amostra por amostra? Porque chamar tua função 48 mil vezes por segundo é absurdamente caro (overhead de chamada de função, context switch, etc.). Mas chamar 750 vezes por segundo entregando 64 amostras por vez é tranquilo. Bloco é eficiência.

Quanto tempo cada bloco tem de orçamento?

fórmulaaritmética
orçamento = block_size / sample_rate

// Exemplos a 48 kHz:
block = 32   → 0.67 ms  (super baixa latência, CPU alta)
block = 64   → 1.33 ms  (baixa latência, equilibrado)
block = 128  → 2.67 ms  (razoável)
block = 256  → 5.33 ms  (confortável)
block = 512  → 10.67 ms (streaming, música não-crítica)
block = 1024 → 21.33 ms (arquivo, rendering)
Uso Block size Por quê
Tocar guitarra com amp sim32-64Músico percebe > 5ms como atraso
Mixer live ao vivo32-128Depende da CPU e tolerância
Live streaming (OBS)256-512Latência não importa, estabilidade importa
Mixing em DAW512-2048Offline, pode ser grande
Seus primeiros testes512Folga pra experimentar sem glitch
Regra prática

Comece com block size 512 ou 256. Depois que o código funcionar estável, reduza pra 128, 64. Cada redução cobra mais CPU e mais disciplina no código.

§ 04

Latência: onde cada milissegundo aparece.

Quando alguém fala "latência de 5ms", isso é raramente um número único. É a soma de várias parcelas que se acumulam.

FaseLatência típicaOnde mora
Microfone → capsula~0 msFísico, desprezível
Conversor A/D (ADC)0.5–2 msHardware da interface
Driver / USB transfer1–3 msOS + driver da interface
Input bufferblock_size / srSistema operacional
Seu callback processa< block_size / srSeu código
Output bufferblock_size / srSistema operacional
Driver / USB transfer1–3 msOS + driver
Conversor D/A (DAC)0.5–2 msHardware da interface

Round-trip típico numa interface USB decente, block 128 @ 48kHz:

exemplo realaritmética
ADC:        1.0 ms
USB in:     1.5 ms
input buf:  2.67 ms (128/48000)
processing: 0.5 ms (seu código)
output buf: 2.67 ms
USB out:    1.5 ms
DAC:        1.0 ms
──────────────────
TOTAL:      ~10.8 ms round-trip
Na prática para teus projetos

Pra live streaming (OBS), 10-30 ms é perfeitamente aceitável — ninguém percebe. Pra mixer live em igreja, até 7-8 ms é aceitável. Pra guitarrista tocando com amp sim, precisa < 5 ms ou o músico reclama.

§ 05

As regras de ouro do código de áudio.

Dentro do audio callback, certas operações são proibidas. Não porque dão erro de compilação, mas porque podem demorar milissegundos ou mais em situações de estresse, e isso quebra o áudio.

Proibições absolutas
  • Alocar memória (Box::new, Vec::new, String::from). Alocação pode bloquear se o heap estiver fragmentado.
  • Desalocar memória (drop de qualquer coisa com heap).
  • Pegar mutex / lock que pode bloquear.
  • Fazer I/O — ler arquivo, escrever log, chamar rede.
  • Dormir (thread::sleep, await em async code).
  • println! em produção. É I/O em stdout, tem lock interno.
Operações seguras
  • Matemática com tipos primitivos: f32, f64, i32.
  • Ler e escrever em buffers pré-alocados: Vec<f32> já criado, arrays fixos, slices.
  • Atomics (AtomicBool, AtomicU32) pra comunicar com outras threads sem lock.
  • Lock-free queues: thread de controle empurra eventos, thread de áudio consome.

Então como a UI muda parâmetros?

A resposta é: comunicação assíncrona via atomics ou lock-free queues. A UI (em outra thread) escreve num atomic. O callback lê esse atomic no início do próximo bloco.

padrão básicorust
use std::sync::atomic::{AtomicU32, Ordering};
use std::sync::Arc;

// Thread da UI escreve:
let gain_atomic = Arc::new(AtomicU32::new(0));
let gain_value: f32 = 0.5;
gain_atomic.store(gain_value.to_bits(), Ordering::Relaxed);

// Thread do áudio lê (dentro do callback):
let gain_bits = gain_atomic.load(Ordering::Relaxed);
let gain = f32::from_bits(gain_bits);
§ 06

cpal: Rust conversa com tua interface.

Pra teu código Rust conversar com a interface USB, você precisa de uma biblioteca que abstraia o sistema operacional. Cada OS tem uma API diferente: CoreAudio no macOS, WASAPI/ASIO no Windows, ALSA/JACK/PipeWire no Linux.

cpal (Cross-Platform Audio Library) é a crate padrão do ecossistema Rust pra isso. Ela te dá uma API única que funciona nos três sistemas.

O Módulo 03 mergulha na stack de áudio do sistema operacional — PortAudio, JACK, PipeWire, ALSA — e explica o que cpal está fazendo por baixo. § 07
Experimento prático

Passthrough ao vivo com medição de latência.

Objetivo: áudio entra pela tua interface, passa pelo teu código Rust, sai pela mesma interface. Com três variações progressivas: (1) passthrough puro, (2) passthrough com ganho, (3) medição de latência real via loopback de cabo.

Pré-requisito

  • Interface USB class-compliant (Scarlett, Audient, MOTU, etc.) — ou a built-in do notebook
  • Fone (não use alto-falantes — feedback é feio)

use cpal::traits::{DeviceTrait, HostTrait};

fn main() -> anyhow::Result<()> {
    let host = cpal::default_host();

    println!("=== DISPOSITIVOS DE ENTRADA ===");
    for device in host.input_devices()? {
        let name = device.name().unwrap_or_else(|_| "?".into());
        println!("  → {}", name);
        if let Ok(config) = device.default_input_config() {
            println!("    {} canais, {} Hz, {:?}",
                config.channels(),
                config.sample_rate().0,
                config.sample_format());
        }
    }

    println!("\n=== DISPOSITIVOS DE SAÍDA ===");
    for device in host.output_devices()? {
        let name = device.name().unwrap_or_else(|_| "?".into());
        println!("  → {}", name);
    }

    Ok(())
}

Passo 4 — Passthrough

src/main.rs — passthroughrust
use cpal::traits::{DeviceTrait, HostTrait, StreamTrait};
use ringbuf::{HeapRb, traits::{Producer, Consumer, Split}};

fn main() -> anyhow::Result<()> {
    let host = cpal::default_host();
    let input_device = host.default_input_device()
        .ok_or_else(|| anyhow::anyhow!("sem entrada"))?;
    let output_device = host.default_output_device()
        .ok_or_else(|| anyhow::anyhow!("sem saída"))?;

    println!("In:  {}", input_device.name()?);
    println!("Out: {}", output_device.name()?);

    let config: cpal::StreamConfig = input_device.default_input_config()?.into();

    let ring = HeapRb::<f32>::new(9600);
    let (mut producer, mut consumer) = ring.split();

    let input_stream = input_device.build_input_stream(
        &config,
        move |data: &[f32], _| {
            for &sample in data {
                let _ = producer.try_push(sample);
            }
        },
        |err| eprintln!("erro input: {}", err),
        None,
    )?;

    let output_stream = output_device.build_output_stream(
        &config,
        move |data: &mut [f32], _| {
            for sample in data.iter_mut() {
                *sample = consumer.try_pop().unwrap_or(0.0);
            }
        },
        |err| eprintln!("erro output: {}", err),
        None,
    )?;

    input_stream.play()?;
    output_stream.play()?;

    println!("Passsthrough rodando. Ctrl+C pra parar.");
    std::thread::park();
    Ok(())
}

Passo 5 — Medir latência (com cabo loopback)

Conecte um cabo físico do headphone out direto pro mic in. O código abaixo gera clicks e mede quanto tempo demoram pra voltar.

src/main.rs — medidorrust
use cpal::traits::{DeviceTrait, HostTrait, StreamTrait};
use std::sync::atomic::{AtomicU64, Ordering};
use std::sync::Arc;
use std::time::Instant;

fn main() -> anyhow::Result<()> {
    let host = cpal::default_host();
    let input_device = host.default_input_device().unwrap();
    let output_device = host.default_output_device().unwrap();
    let config: cpal::StreamConfig = input_device.default_input_config()?.into();

    let start = Instant::now();
    let click_time_us = Arc::new(AtomicU64::new(0));

    let sample_rate = config.sample_rate.0 as u64;
    let mut sample_count: u64 = 0;
    let click_interval = sample_rate * 2;

    let click_time_out = Arc::clone(&click_time_us);
    let output_stream = output_device.build_output_stream(
        &config,
        move |data: &mut [f32], _| {
            for sample in data.iter_mut() {
                let is_click = sample_count % click_interval < 24;
                if is_click && sample_count % click_interval == 0 {
                    let now = start.elapsed().as_micros() as u64;
                    click_time_out.store(now, Ordering::Relaxed);
                }
                *sample = if is_click { 0.8 } else { 0.0 };
                sample_count += 1;
            }
        },
        |err| eprintln!("{}", err),
        None,
    )?;

    let click_time_in = Arc::clone(&click_time_us);
    let input_stream = input_device.build_input_stream(
        &config,
        move |data: &[f32], _| {
            for &sample in data {
                if sample.abs() > 0.3 {
                    let now = start.elapsed().as_micros() as u64;
                    let sent = click_time_in.load(Ordering::Relaxed);
                    if sent > 0 && now > sent {
                        println!("Latência: {:.2} ms",
                            (now - sent) as f64 / 1000.0);
                        click_time_in.store(0, Ordering::Relaxed);
                    }
                    break;
                }
            }
        },
        |err| eprintln!("{}", err),
        None,
    )?;

    input_stream.play()?;
    output_stream.play()?;
    std::thread::park();
    Ok(())
}

A cada 2 segundos você vê a latência real medida. Anote — esse é o número que te interessa pro projeto.

Glossário
AUDIO CALLBACK
Função que o sistema de áudio chama repetidamente pra entregar amostras de entrada e pedir amostras de saída.
BLOCK SIZE
Quantas amostras são processadas por chamada de callback. Também chamado buffer size, period size, frames per buffer.
ROUND-TRIP LATENCY
Tempo total entre o som entrar na interface e sair de volta.
LOCK-FREE
Algoritmo que não usa mutex/lock, funciona com atomics. Essencial pra callback de áudio.
RING BUFFER
Buffer circular onde uma thread escreve e outra lê, sem precisar de lock.
XRUN
Quando o callback demora demais e o áudio glitcha. Sempre ruim.
cpal
Crate Rust cross-platform pra acesso a dispositivos de áudio.
