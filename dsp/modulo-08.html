Módulo 08 — Modelo conceitual

Threading e lock-free.

A thread de áudio nunca pode esperar. A thread de UI faz coisas lentas (I/O, alocação, banco de dados). Como elas conversam sem que uma mate a outra? Atomics, ring buffers e padrões de mensagem. Este módulo é a base arquitetural de tudo no mixer.

§ 01

O cliente não pode esperar pelo banco.

Imagina um restaurante. O cliente quer um prato em 10 minutos. O restaurante tem um chef principal (a thread de áudio) que precisa estar 100% focado em cozinhar — qualquer interrupção atrapalha o prato. E tem um gerente (a thread de UI) que cuida de pedidos, cardápio, conversa com clientes, atende fornecedor, anota encomendas pra amanhã.

Se o cliente entra na cozinha pra fazer pedido direto pro chef, o chef para de cozinhar. Atrasa todos os pratos. Comida queima.

A solução real do restaurante: existe uma comanda, um pedaço de papel onde o gerente escreve o pedido e o chef lê quando termina o prato anterior. O gerente nunca espera o chef terminar pra escrever. O chef nunca espera o gerente terminar de escrever pra ler — ele lê quando está pronto.

Esse é o conceito do nosso módulo. UI escreve em uma "comanda" (atomic ou ring buffer). Audio thread lê quando termina o bloco anterior. Nenhum espera o outro.

§ 02

As regras revisitadas.

Reforço do que vimos no Módulo 02. Dentro do audio callback, é proibido:

  • Alocar memória (Vec::new, Box::new, String::from, etc.)
  • Desalocar memória (drop de qualquer coisa com heap)
  • Pegar mutex ou qualquer lock que possa bloquear
  • Fazer I/O — arquivo, rede, log, terminal
  • Dormir (thread::sleep, await)
  • println! ou qualquer função com lock interno

Por quê: qualquer dessas operações pode demorar muito mais do que o orçamento de tempo do bloco (algumas dezenas de microssegundos a milissegundos). Se o callback demora demais, o áudio glitcha — click, pop ou silêncio.

O que se pode fazer:

  • Matemática com tipos primitivos (f32, i32, etc.)
  • Acessar arrays e Vec já alocados
  • Operações em atomics (load/store)
  • Push/pop em ring buffers SPSC lock-free
  • Ler de slices imutáveis

Tudo o resto fica fora do callback — em uma thread separada que tem todas as liberdades.

Cuidado com mutexes "rápidos"

Tem gente que argumenta "pego o mutex só por 1 microssegundo, é seguro". Não é. Sob carga ou contenção, esse mutex pode esperar 100ms se a outra thread foi escalonada e o sistema operacional não a trouxe de volta. Áudio com glitch ocasional sob carga é um bug que aparece em produção e não no seu desktop. Mutex é simplesmente banido.

§ 03

Topologia de threads.

O mixer real tem mais de duas threads. Mapa completo:

Topologia de threads. Audio thread no topo, isolada. Demais threads se comunicam com ela apenas via canais lock-free.

Função de cada thread

  • Audio thread: única que pode estar no callback. Roda em prioridade real-time. Faz só processamento de áudio.
  • UI thread: roda a interface (Tauri, ou web local). Recebe ações do usuário, atualiza estado de UI.
  • Control thread: thread intermediária que recebe mudanças de UI, faz cálculos pesados (coeficientes de filtros, conversões dB↔linear), e empurra resultado pronto pro audio thread.
  • Network thread: cuida de RTP (pacotes pra rede), OSC (controle remoto), WebSocket (UI remota). Recebe áudio do audio thread, manda pra rede.
  • Disk thread: salva e carrega presets, snapshots de show, gravações de áudio. Operações lentas que nunca tocam o audio thread.

Por que separar control de UI

UI thread em Tauri ou web pode ficar congelada por 50ms processando um evento de mouse, esperando IPC, fazendo render. Não dá pra calcular coeficientes do biquad ali — mesmo sem ser real-time, esses 50ms podem causar lag perceptível na sensação do fader.

Control thread fica entre os dois. Recebe "fader subiu pra -6 dB" da UI, calcula instantaneamente os 5 coeficientes do biquad equivalente, e empurra pro audio thread. A UI continua livre pra renderizar; o audio thread recebe o pacote pronto.

§ 04

Atomics: o pulo do gato.

Pra um único valor primitivo (um float, um int, um bool), atomics são a primitiva mais simples e eficiente.

O que é um atomic

Atomic é uma variável que o hardware garante ler e escrever de forma indivisível — sem que outra thread veja um estado intermediário. Em CPUs modernas, isso é uma instrução assembly com prefixo de "lock" ou "memory barrier".

Em Rust, atomics estão em std::sync::atomic:

uso de atomicrust
use std::sync::atomic::{AtomicU32, Ordering};
use std::sync::Arc;

// Compartilhado entre threads
let gain = Arc::new(AtomicU32::new(1.0_f32.to_bits()));

// UI thread escreve:
let gain_ui = Arc::clone(&gain);
gain_ui.store(0.5_f32.to_bits(), Ordering::Relaxed);

// Audio thread lê:
let gain_audio = Arc::clone(&gain);
let g = f32::from_bits(gain_audio.load(Ordering::Relaxed));

Por que AtomicU32 pra um f32?

Rust stable não tem AtomicF32. Truque: representar o float como os 32 bits crus dele, salvar como u32 atômico. to_bits() e from_bits() fazem essa conversão sem nenhum custo (são reinterpretação direta).

Memory ordering

O parâmetro Ordering diz quão estritamente o compilador e a CPU devem sincronizar essa operação com outras. Quatro níveis:

OrderingCustoQuando usar
RelaxedQuase zeroValores independentes (parâmetro solto)
Acquire / ReleasePequenoSincronizar com outro dado (flag + dado)
AcqRelPequenoRead-modify-write sincronizado
SeqCstMais altoQuando em dúvida (ou nunca pra real-time)

Pra nosso caso (UI escreve, audio lê, valor independente): Relaxed é o certo. É efetivamente "free" no x86 (uma instrução normal de mov), e não impõe barreiras desnecessárias.

Quando atomic não basta

Pra mandar mais de um valor "atomically together" — tipo os 5 coeficientes do biquad, que precisam ser aplicados todos juntos ou nenhum — atomics individuais não bastam. Aí entra ring buffer SPSC.

§ 05

Ring buffer SPSC.

SPSC = Single Producer, Single Consumer. Estrutura de dados especificamente desenhada pra ter exatamente uma thread escrevendo e exatamente uma thread lendo, sem mutex.

Como funciona

É um array circular de tamanho fixo, com dois ponteiros (head e tail) que são atomics. O produtor avança head ao escrever. O consumidor avança tail ao ler. Quando head == tail, fila vazia. Quando head + 1 == tail (com wrap), fila cheia.

Ring buffer SPSC. Tail aponta pra próxima leitura. Head aponta pra próxima escrita. Mensagens entre os ponteiros estão "em voo".

Garantias

  • Produtor nunca espera. push() escreve no slot do head e avança. Se cheio, retorna erro imediato.
  • Consumidor nunca espera. pop() lê do slot do tail e avança. Se vazio, retorna None imediato.
  • Sem mutex. Apenas atomics nas posições.
  • Não preserva ordem entre múltiplos produtores ou consumidores. Por isso é "SPSC".

Crates Rust

  • rtrb — Real-Time Ring Buffer. Foco em real-time, sem alocação durante uso.
  • ringbuf — Mais features (SPMC, MPSC), API similar.

Pra audio thread, rtrb é a escolha defensável. Foi feita exatamente pra isso.

uso básico do rtrbrust
use rtrb::RingBuffer;

// Setup (fora do callback)
let (mut producer, mut consumer) =
    RingBuffer::<ParameterUpdate>::new(256);

// Control thread:
producer.push(ParameterUpdate { ... }).ok();

// Audio thread (no callback):
while let Ok(update) = consumer.pop() {
    // processa
}
§ 06

Padrões de mensagem.

Padrão 1 — Fire-and-forget de parâmetro

Mais comum. UI muda algo, manda mensagem, esquece. Audio thread aplica quando lê.

fire-and-forgetrust
enum ParameterMessage {
    SetChannelGain { channel: u8, db: f32 },
    SetChannelPan { channel: u8, pan: f32 },
    SetChannelMute { channel: u8, muted: bool },
    SetEqBand { channel: u8, band: u8, coefs: BiquadCoefs },
    SetCompressor { channel: u8, params: CompParams },
    // ... etc
}

Tudo num único enum, single ring buffer entre control thread e audio thread.

Padrão 2 — Hot reload de buffers

Pra coisas grandes (IR de reverb, lookup table de waveshaper), você não pode mandar pelo ringbuf direto — ocupa muita memória e copia caro.

Solução: swap atômico de Arc. UI/control thread aloca o buffer novo, encapsula em Arc<[f32]>, troca atomicamente o ponteiro que o audio thread está lendo. Audio thread descarta o velho automaticamente quando reduce o refcount.

swap atômico de bufferrust
use arc_swap::ArcSwap;
use std::sync::Arc;

// Compartilhado
let ir_buffer = Arc::new(ArcSwap::from_pointee(vec![0.0_f32; 48_000]));

// UI thread troca:
let new_ir = load_impulse_response("cathedral.wav");
ir_buffer.store(Arc::new(new_ir));

// Audio thread lê (no callback):
let ir = ir_buffer.load();
// ir é Arc<Vec<f32>>, válido durante o bloco
for &sample in ir.iter() {
    // processa
}

Cuidado: o drop do Arc velho pode acontecer no audio thread se for o último refcount caindo. Solução: garantir que a control thread mantenha referência por pelo menos um bloco depois do swap, ou usar uma queue de deferred-drop pra liberar buffers fora do callback.

Padrão 3 — Request/response (raro)

Pra coisas onde a UI precisa de uma resposta do audio thread (raro). Por exemplo: "qual o pico atual do canal 5 nos últimos 100ms?".

Solução: dois ring buffers. Um pra request da UI pro audio. Outro pra response do audio pra UI. Audio thread responde no próximo bloco, UI thread pega quando puder.

Pra V1 do mixer, evitar esse padrão. Use atomics pra meters (próxima seção). Request/response complica e raramente é necessário.

§ 07

Caminho reverso: meters.

Até agora falamos de UI → audio. Mas também precisa de audio → UI: a UI quer mostrar VU meters em tempo real, indicador de clip, peak hold, atividade dos canais.

Atomics como solução elegante

Cada canal tem um AtomicU32 com o pico atual (em bits de f32). Audio thread atualiza a cada bloco. UI thread lê quando renderiza (60Hz, 30Hz, o que for). Não precisa ring buffer porque não precisa preservar histórico — só importa o valor atual.

peak meter atomicrust
pub struct PeakMeter {
    peak: AtomicU32,        // pico do bloco atual
    peak_hold: AtomicU32,   // pico mantido por ~1s
    hold_counter: AtomicU32,
}

impl PeakMeter {
    // Audio thread chama no fim do bloco
    pub fn update(&self, block_peak: f32) {
        self.peak.store(block_peak.to_bits(), Ordering::Relaxed);

        let current_hold = f32::from_bits(self.peak_hold.load(Ordering::Relaxed));
        if block_peak > current_hold {
            self.peak_hold.store(block_peak.to_bits(), Ordering::Relaxed);
            self.hold_counter.store(48000, Ordering::Relaxed); // 1s de hold
        } else {
            let count = self.hold_counter.load(Ordering::Relaxed);
            if count > 0 {
                self.hold_counter.store(count.saturating_sub(128), Ordering::Relaxed);
            } else {
                self.peak_hold.store(block_peak.to_bits(), Ordering::Relaxed);
            }
        }
    }

    // UI thread chama quando renderiza
    pub fn read(&self) -> (f32, f32) {
        let peak = f32::from_bits(self.peak.load(Ordering::Relaxed));
        let hold = f32::from_bits(self.peak_hold.load(Ordering::Relaxed));
        (peak, hold)
    }
}

32 canais × 2 atomics + 32 buses × 2 atomics = ~128 atomics. Custo desprezível. UI tem dados sempre frescos.

arquitetura geralrust
pub struct AudioEngine {
    mixer: Mixer,
    // Recebimento de comandos da UI/control
    command_rx: Consumer<Command>,
    // Envio de meters pra UI
    meters: Arc<MetersSnapshot>,
}

pub struct MetersSnapshot {
    channels: [PeakMeter; 32],
    buses: [PeakMeter; 11],
    master: PeakMeter,
}

impl AudioEngine {
    // Chamado pelo callback do cpal
    pub fn process_block(
        &mut self,
        inputs: &[&[f32]],
        outputs: &mut [&mut [f32]],
    ) {
        // 1. Drena comandos
        while let Ok(cmd) = self.command_rx.pop() {
            self.apply_command(cmd);
        }

        // 2. Processa áudio
        self.mixer.process_block(inputs, outputs);

        // 3. Atualiza meters
        self.update_meters(outputs);
    }
}

pub struct ControlThread {
    command_tx: Producer<Command>,
    // Estado replicado pra cálculos
    state: MixerState,
}

impl ControlThread {

        match event {

                let coefs = calculate_biquad_coefs(fc, q, gain, 48000.0);
                self.command_tx.push(Command::SetEqBand { channel, band, coefs }).ok();
            }

        }
    }
}
§ 09

Decisões arquiteturais.

Threads do V1

  • Audio thread: cpal callback, real-time priority
  • Control thread: tokio task
  • UI thread: Tauri main thread
  • Network thread: tokio task (RTP, OSC, WS)
  • Disk thread: tokio task (lazy)

Crates

  • rtrb — ring buffer SPSC entre control e audio
  • arc-swap — hot reload de buffers grandes
  • tokio — runtime das outras threads
  • std::sync::atomic — meters e flags simples

Tamanho do ring buffer

  • Control → audio: 256 mensagens. Cada bloco drena tudo, então 256 é margem grande.
  • Network → audio (futuro RTP receive): 64 blocos de áudio. Suficiente pra 100ms de jitter.

Real-time priority

  • cpal já configura prioridade real-time no callback automaticamente
  • Linux: precisa do user em audio group e /etc/security/limits.d/audio.conf com rtprio 99
  • Windows: cpal cuida sozinho via WASAPI exclusive

Erro tratamento no callback

  • Nunca panic dentro do callback — encerraria stream do cpal
  • Bugs de runtime devem ser logados via atomic flag, lidos pela control thread, e printados ali
  • Callback usa .unwrap_or(default) ou matches explícitos, nunca .unwrap()
Glossário
AUDIO THREAD
Thread onde o callback do cpal roda. Real-time priority. Restrições estritas de operações permitidas.
CONTROL THREAD
Thread intermediária entre UI e audio. Faz cálculos pesados pra liberar a UI e prepara mensagens pro audio thread.
LOCK-FREE
Algoritmo que não usa mutex/lock. Funciona com atomics. Garante que nenhuma thread fica bloqueada esperando outra.
WAIT-FREE
Subset de lock-free onde toda operação termina em tempo bounded. Mais forte que lock-free.
ATOMIC
Variável que o hardware lê/escreve indivisivelmente. AtomicU32, AtomicBool, etc.
MEMORY ORDERING
Garantia de sincronização de uma operação atomic com outras operações. Relaxed é o mais fraco.
SPSC
Single Producer, Single Consumer. Ring buffer com exatamente uma thread escrevendo e uma lendo.
RING BUFFER
Buffer circular de tamanho fixo, com head e tail atomics. Estrutura padrão pra fila lock-free.
FIRE-AND-FORGET
Padrão de mensagem onde o produtor envia e não espera resposta.
HOT RELOAD
Trocar buffer grande durante runtime sem alocar no audio thread. Usa swap atômico de Arc.
METER
Indicador visual de nível de áudio. Atualizado pelo audio thread, lido pela UI.
PEAK HOLD
Comportamento de meter onde o pico fica mantido por ~1s antes de cair. Permite ler picos rápidos.
RT PRIORITY
Real-Time Priority. Configuração do scheduler do OS pra dar prioridade máxima ao audio thread.
