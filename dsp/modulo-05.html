Módulo 05 — Controle contínuo

Fader, smoothing e pan.

Parece banal — é só multiplicar por um número, certo? Não. Multiplicar por número variável em tempo real é onde a maioria dos DSPs amadores estragam o áudio com "zipper noise". Este módulo mostra o porquê, a física do ouvido envolvida, e três níveis de solução.

§ 01

O clique que ninguém queria.

Experimento mental: pega o passthrough do Módulo 02, adiciona uma variável gain: f32 = 1.0 e multiplica cada amostra por ela. Depois, no meio do áudio rodando, muda o gain de 1.0 pra 0.3 de uma só vez. O que acontece?

Click. Um estalo feio, curto, audível. Acabou de acontecer um degrau na amplitude — a amostra N-1 tava multiplicada por 1.0, a amostra N foi multiplicada por 0.3. Diferença abrupta demais. Isso é uma descontinuidade no sinal, e o ouvido traduz descontinuidade como click.

Onda antes da mudança (esquerda): amplitude plena. Depois (direita): amplitude reduzida. O degrau no ponto de mudança gera um click audível.

Isso é o fenômeno chamado zipper noise quando acontece continuamente — imagine mover um fader físico devagar com a mão. Cada pequeno incremento do valor gera um micro-click, e a sequência desses micro-clicks soa como um "zíper" rasgando. Por isso o nome.

A solução parece óbvia: em vez de mudar o ganho abruptamente, interpolar o valor gradualmente de onde estava até onde vai. Mas existem três formas de fazer essa interpolação, e cada uma tem seu lugar.

Por que isso importa pro produto real

Um mixer digital sem smoothing bem feito soa "digital" no pior sentido. Engenheiro de som experiente sente na hora. Um dos motivos pelos quais mesas digitais baratas soam "inferiores" a mesas analógicas não é a qualidade dos componentes — é que os faders não fazem smoothing direito. Fazer smoothing certo é barato em CPU e faz diferença enorme na percepção.

§ 02

Por que dB é obrigatório.

Antes de falar de curvas e smoothing, precisa entender uma coisa sobre o ouvido humano: ele não percebe volume linearmente. Ele percebe volume logaritmicamente.

Concreto: dobrar a amplitude (de 0.25 pra 0.5) não soa como "duas vezes mais alto". Soa como "um pouquinho mais alto". Pra soar "duas vezes mais alto", você precisa aumentar 10x a amplitude. Pra soar "quatro vezes mais alto", 100x.

Essa curva logarítmica é tão universal em áudio que inventaram uma unidade só pra ela: o decibel (dB).

dB = 20 · log₁₀(amplitude)
Converte uma amplitude linear (0 a 1+) em decibéis. Ex: amplitude 1.0 = 0 dB (referência). Amplitude 0.5 = -6 dB. Amplitude 0.0 = -∞ dB.

fn db_to_linear(db: f32) -> f32 {
    10.0_f32.powf(db / 20.0)
}

// amplitude linear pra dB
fn linear_to_db(linear: f32) -> f32 {

}

fn linear_to_db_safe(linear: f32) -> f32 {
    if linear <= 1e-9 {
        -144.0  // "-inf" prático
    } else {
        20.0 * linear.log10()
    }
}
Regra prática

Fader na UI mostra e recebe dB (porque é o que o operador pensa: "vou tirar 3 dB desse canal"). Motor de áudio multiplica em linear (porque é o que a matemática precisa). A conversão acontece uma vez, quando o valor novo chega da UI, antes de entrar no atomic ou ring buffer.

§ 03

Curvas de fader: linear soa errado.

Imagine um fader de mesa com curso físico de 0 a 100mm. A pergunta: quando o dedo do operador está na posição 50mm (meio do curso), que ganho o áudio deve ter?

Resposta ingênua — linear

50% do curso = 50% da amplitude (0.5 linear). Parece lógico, mas soa péssimo. O fader fica inútil: quase todo o controle sonoro acontece nos últimos 10mm perto do topo. Os primeiros 90mm do curso parecem quase a mesma coisa — tudo muito baixo, quase silencioso.

Razão: o ouvido é logarítmico. Amplitude 0.5 soa como "um pouco mais baixo", não como "metade do volume".

Resposta correta — curva de console

O curso do fader deve mapear em dB, não em amplitude linear. Uma curva típica de mesa:

Posição do faderdBAmplitude linear
100% (topo)+10 dB3.16
75%0 dB (unity)1.0
50% (meio)-10 dB0.316
25%-30 dB0.0316
10%-50 dB0.00316
0% (fundo)-∞ dB0.0

Perceba: a posição de unity (0 dB) fica em 75% do curso, não no meio. Isso deixa "headroom" pro operador subir o fader além do unity quando precisa, e reserva a maior parte do curso pra ajustes finos abaixo de unity — que é onde o operador passa 95% do tempo.

Curva linear (vermelho pálido) vs curva de console (laranja). Unity em 75% do curso.

A fórmula prática

Existem várias curvas usadas em mesas diferentes. Uma que funciona bem pra console digital é um mapeamento por segmentos:

curva de faderrust
// Recebe posição do fader (0.0 a 1.0) e retorna dB
fn fader_position_to_db(pos: f32) -> f32 {
    let pos = pos.clamp(0.0, 1.0);

    if pos <= 0.0 {
        -144.0  // silêncio
    } else if pos <= 0.25 {
        // Segmento inferior: -∞ a -30 dB (aceleração rápida perto do zero)
        let t = pos / 0.25;
        -60.0 + 30.0 * t
    } else if pos <= 0.75 {
        // Segmento médio: -30 dB a 0 dB (aceleração linear)
        let t = (pos - 0.25) / 0.50;
        -30.0 + 30.0 * t
    } else {
        // Segmento superior: 0 dB a +10 dB (aceleração lenta)
        let t = (pos - 0.75) / 0.25;
        10.0 * t
    }
}

Diferentes fabricantes usam curvas diferentes. YAMAHA, Allen & Heath, Midas, todas têm suas fórmulas proprietárias. A curva acima é "razoável" — boa pra começar, e o operador se adapta rápido. Mais tarde você pode calibrar com feedback de engenheiros de som.

§ 04

Smoothing: três abordagens.

Agora a pergunta central: como fazer o ganho variar gradualmente entre o valor atual e o valor novo, sem click, sem zipper?

Abordagem 1 — Linear ramp

A mais simples: quando chega um valor novo, interpolar linearmente ao longo de N amostras.

linear ramprust
struct LinearRamp {
    current: f32,
    target:  f32,
    step:    f32,
    remaining_samples: u32,
}

impl LinearRamp {
    pub fn set_target(&mut self, target: f32, ramp_samples: u32) {
        self.target = target;
        self.remaining_samples = ramp_samples;
        self.step = (target - self.current) / ramp_samples as f32;
    }

    pub fn next(&mut self) -> f32 {
        if self.remaining_samples > 0 {
            self.current += self.step;
            self.remaining_samples -= 1;
        } else {
            self.current = self.target;
        }
        self.current
    }
}

Prós: super simples, previsível, exatamente N amostras até chegar. Contras: o valor interpolado é em linear, mas o ouvido percebe em log. Uma rampa linear de -60 dB pra 0 dB passa 90% do tempo perto de -60 dB (inaudível) e chega rápido demais no meio. Soa "corrido".

Abordagem 2 — One-pole smoother (filtro exponencial)

A abordagem DSP elegante. Um filtro de um pólo faz o valor atual se aproximar exponencialmente do target. A matemática é:

y[n] = α · target + (1 − α) · y[n−1]
α é o coeficiente de suavização, entre 0 e 1. Pequeno = muito suave (lento). Grande = pouco suave (rápido).
one-pole smootherrust
struct OnePole {
    current: f32,
    target:  f32,
    alpha:   f32,
}

impl OnePole {
    // tau é o tempo em segundos pra alcançar ~63% do target
    pub fn new(tau_seconds: f32, sample_rate: f32) -> Self {
        let alpha = 1.0 - (-1.0 / (tau_seconds * sample_rate)).exp();
        Self { current: 0.0, target: 0.0, alpha }
    }

    pub fn set_target(&mut self, target: f32) {
        self.target = target;
    }

    pub fn next(&mut self) -> f32 {
        self.current += self.alpha * (self.target - self.current);
        self.current
    }
}

Prós: 3 operações por amostra, soa natural, não precisa saber quantos samples durar (sempre converge no ritmo certo). Resposta parece exponencial, o que bate bem com percepção log do ouvido. Contras: tecnicamente nunca chega exatamente no target (só assintoticamente). Na prática, após ~5·tau, a diferença é imensurável.

Valores típicos de tau:

  • 10ms — rápido, bom pra ganho de canal
  • 50-100ms — médio, bom pra panorama
  • 300ms+ — lento, bom pra efeitos de fade tipo "cross-fade"

Abordagem 3 — One-pole com snap detection

A versão profissional: combina o one-pole (pra mudanças pequenas, suaves) com uma detecção de "mudança grande" que aplica uma rampa mais agressiva ou um cross-fade.

Por quê? Se o operador tira um canal de unity pra -∞ (derruba o fader), one-pole com tau de 20ms demora 100ms pra realmente silenciar. Nesse meio tempo você ouve um "fade out" indesejado. Em casos críticos (drop de mute), você quer reação imediata.

smoother pro-audiorust
struct ProSmoother {
    smoother: OnePole,
    last_target: f32,
    // threshold em dB linear pra "mudança grande"
    snap_threshold: f32,
}

impl ProSmoother {
    pub fn set_target(&mut self, target: f32) {
        let delta = (target - self.last_target).abs();

        if delta > self.snap_threshold {
            // Mudança grande: snap (ou cross-fade em outra versão)
            self.smoother.current = target;
        }

        self.smoother.set_target(target);
        self.last_target = target;
    }
}

Na prática, o Módulo 05 vai usar a Abordagem 2 (one-pole), que é o sweet-spot entre simplicidade e qualidade. A Abordagem 3 é pra quando você tá refinando o produto final.

§ 05

Implementação lado a lado.

Fader completo (com smoothing embutido) nas duas trilhas. A diferença de esforço fica gritante aqui.

Rust

Struct do fader com one-pole smoother integrado e API em dB.

fader.rsrust
pub struct Fader {
    smoother: OnePole,
    sample_rate: f32,
}

impl Fader {
    pub fn new(sample_rate: f32) -> Self {
        let mut smoother = OnePole::new(0.02, sample_rate);
        smoother.current = 1.0;  // unity
        smoother.set_target(1.0);
        Self { smoother, sample_rate }
    }

    pub fn set_gain_db(&mut self, db: f32) {
        let linear = if db <= -90.0 {
            0.0
        } else {
            10.0_f32.powf(db / 20.0)
        };
        self.smoother.set_target(linear);
    }

    pub fn set_position(&mut self, pos: f32) {
        let db = fader_position_to_db(pos);
        self.set_gain_db(db);
    }

    // Hot loop: uma multiplicação + smoother
    pub fn process(&mut self, x: f32) -> f32 {
        let gain = self.smoother.next();
        x * gain
    }
}

30 linhas (mais as dependências OnePole e fader_position_to_db). API clara, comportamento previsível.

§ 06

Pan: o fader espacial.

Se fader controla "quanto alto", pan controla "onde no palco estéreo". Esquerda (L), centro (C), direita (R). Uma posição entre -1.0 (totalmente L) e +1.0 (totalmente R), com 0.0 sendo o centro.

Pan é, matematicamente, dois faders controlados juntos: um pra saída esquerda, outro pra saída direita. Conforme você move o controle de pan, os dois ganhos mudam em direções opostas.

Pan como dois ganhos complementares. Pan=0 (centro): ambos em ~70%. Pan=-1 (esquerda total): L=1.0, R=0.0.

A pergunta central é: quanto ganho cada canal tem quando o pan está no centro?

Parece trivial mas é a decisão que separa um pan bom de um pan ruim. Porque é aí que entram as leis de pan.

§ 07

Leis de pan: -3dB, -4.5dB, -6dB.

Se o ganho no centro fosse 1.0 pra ambos os canais, um sinal panado ao centro seria 2x mais alto que o mesmo sinal totalmente à esquerda (que só toca em L). Isso é problema: mexer o pan muda a amplitude percebida.

Pra compensar, o centro recebe um "desconto" de ganho. Esse desconto é a lei de pan, e existem três escolas:

Lei -6 dB (linear)

Mais simples. No centro, cada canal recebe 0.5 de ganho (= -6 dB). Matematicamente:

pan linearrust
// pan: -1.0 (L total) a +1.0 (R total)
fn pan_linear(pan: f32) -> (f32, f32) {
    let pan = pan.clamp(-1.0, 1.0);
    let left = (1.0 - pan) * 0.5;
    let right = (1.0 + pan) * 0.5;
    (left, right)
}

Problema: soa "enfraquecido" no centro. Pan no meio parece mais baixo que pan nas pontas.

Lei -3 dB (constant power, square-root)

No centro, cada canal recebe ~0.707 (= -3 dB). A ideia: a potência total (soma dos quadrados) fica constante conforme o pan move. Isso bate com como o ouvido percebe "mesmo volume" em qualquer posição.

pan constant powerrust
use std::f32::consts::PI;

fn pan_constant_power(pan: f32) -> (f32, f32) {
    let pan = pan.clamp(-1.0, 1.0);
    // Mapeia pan de [-1, 1] pra ângulo [0, π/2]
    let angle = (pan + 1.0) * 0.25 * PI;
    let left = angle.cos();
    let right = angle.sin();
    (left, right)
}

Esta é a lei mais usada em consoles digitais profissionais.

Lei -4.5 dB (compromise)

Meio-termo: no centro, cada canal recebe ~0.6. Um híbrido matemático das duas anteriores. Usada em algumas mesas analógicas clássicas como a Neve.

Recomendação pro teu projeto

Use lei -3 dB (constant power). É o padrão de console digital profissional, soa consistente pro ouvido, e é a expectativa de qualquer engenheiro de som que usar tua mesa. Se um dia quiser oferecer escolha entre leis, faça um parâmetro de configuração — mas -3 dB é o default correto.

Pan estéreo completo (Rust)

Juntando fader + pan num canal estéreo completo:

channel_strip.rsrust
pub struct ChannelStrip {
    fader: Fader,
    pan_smoother: OnePole,
    sample_rate: f32,
}

impl ChannelStrip {
    pub fn new(sample_rate: f32) -> Self {
        let mut pan_smoother = OnePole::new(0.05, sample_rate);
        pan_smoother.current = 0.0;
        pan_smoother.set_target(0.0);

        Self {
            fader: Fader::new(sample_rate),
            pan_smoother,
            sample_rate,
        }
    }

    pub fn set_pan(&mut self, pan: f32) {
        self.pan_smoother.set_target(pan.clamp(-1.0, 1.0));
    }

    pub fn set_gain_db(&mut self, db: f32) {
        self.fader.set_gain_db(db);
    }

    // Input mono, output estéreo (L, R)
    pub fn process(&mut self, x: f32) -> (f32, f32) {
        // 1. Fader primeiro
        let post_fader = self.fader.process(x);

        // 2. Pan (constant power)
        let pan = self.pan_smoother.next();
        let angle = (pan + 1.0) * 0.25 * std::f32::consts::PI;
        let l_gain = angle.cos();
        let r_gain = angle.sin();

        (post_fader * l_gain, post_fader * r_gain)
    }
}

Note a ordem: fader antes, pan depois. Essa é a ordem padrão de mesa. O inverso (pan antes do fader) também é possível mas tem implicações diferentes em efeitos mandados por send — discussão pra outro módulo.

Otimização: evitando sin/cos por amostra

O angle.cos() e angle.sin() dentro do loop são caros. Quando o pan não tá mudando (o smoother convergiu), esses valores são constantes. Otimização comum: só recalcula quando detecta mudança.

versão otimizada (esboço)rust
pub fn process(&mut self, x: f32) -> (f32, f32) {
    let post_fader = self.fader.process(x);

    let pan = self.pan_smoother.next();
    // Só recalcula se mudou significativamente
    if (pan - self.last_pan).abs() > 0.0001 {
        let angle = (pan + 1.0) * 0.25 * PI;
        self.l_gain_cached = angle.cos();
        self.r_gain_cached = angle.sin();
        self.last_pan = pan;
    }

    (post_fader * self.l_gain_cached, post_fader * self.r_gain_cached)
}

Com 32 canais rodando, essa otimização faz diferença mensurável. Em canais que não tão com pan sendo mexido, é quase zero custo.

Passo 3 — main.rs

src/main.rsrust
use cpal::traits::{DeviceTrait, HostTrait, StreamTrait};
use crossterm::event::{read, Event, KeyCode, KeyEvent};
use crossterm::terminal::{enable_raw_mode, disable_raw_mode};
use rtrb::RingBuffer;

mod one_pole;
mod fader;
mod channel;

use channel::ChannelStrip;

// Mensagens da thread de controle pro audio callback
enum ControlMsg {
    SetGainDb(f32),
    SetPan(f32),
    ToggleSmoothing(bool),
}

fn main() -> anyhow::Result<()> {
    // Carrega WAV de teste
    let mut reader = hound::WavReader::open("input.wav")?;
    let spec = reader.spec();
    let samples: Vec<f32> = reader.samples::<i16>()
        .map(|s| s.unwrap_or(0) as f32 / 32768.0)
        .collect();

    let host = cpal::default_host();
    let device = host.default_output_device().unwrap();
    let config: cpal::StreamConfig = device.default_output_config()?.into();
    let sample_rate = config.sample_rate.0 as f32;

    // Canal de mensagens UI → áudio
    let (mut tx, mut rx) = RingBuffer::<ControlMsg>::new(32);

    let mut strip = ChannelStrip::new(sample_rate);
    let mut playhead: usize = 0;
    let mut smoothing_on = true;

    let stream = device.build_output_stream(
        &config,
        move |data: &mut [f32], _| {
            // Drena mensagens de controle
            while let Ok(msg) = rx.pop() {
                match msg {
                    ControlMsg::SetGainDb(db) => strip.set_gain_db(db),
                    ControlMsg::SetPan(p) => strip.set_pan(p),
                    ControlMsg::ToggleSmoothing(on) => smoothing_on = on,
                }
            }

            // Output estéreo interleaved
            for frame in data.chunks_mut(2) {
                let input = samples[playhead];
                playhead = (playhead + 1) % samples.len();

                let (l, r) = strip.process(input);
                frame[0] = l;
                frame[1] = r;
            }
        },
        |err| eprintln!("{}", err),
        None,
    )?;

    stream.play()?;

    // UI thread: lê teclado
    enable_raw_mode()?;

    let mut gain_db: f32 = 0.0;
    let mut pan: f32 = 0.0;

    println!("\rControles:");
    println!("\r  ↑/↓ : fader ±1dB");
    println!("\r  ←/→ : pan");
    println!("\r  M   : mute (drop pra -inf)");
    println!("\r  U   : unity (0 dB, pan centro)");
    println!("\r  Q   : sair");

    loop {
        if let Event::Key(KeyEvent { code, .. }) = read()? {
            match code {
                KeyCode::Up => {
                    gain_db = (gain_db + 1.0).min(10.0);
                    let _ = tx.push(ControlMsg::SetGainDb(gain_db));
                }
                KeyCode::Down => {
                    gain_db = (gain_db - 1.0).max(-60.0);
                    let _ = tx.push(ControlMsg::SetGainDb(gain_db));
                }
                KeyCode::Left => {
                    pan = (pan - 0.1).max(-1.0);
                    let _ = tx.push(ControlMsg::SetPan(pan));
                }
                KeyCode::Right => {
                    pan = (pan + 0.1).min(1.0);
                    let _ = tx.push(ControlMsg::SetPan(pan));
                }
                KeyCode::Char('m') | KeyCode::Char('M') => {
                    gain_db = -144.0;
                    let _ = tx.push(ControlMsg::SetGainDb(gain_db));
                }
                KeyCode::Char('u') | KeyCode::Char('U') => {
                    gain_db = 0.0;
                    pan = 0.0;
                    let _ = tx.push(ControlMsg::SetGainDb(0.0));
                    let _ = tx.push(ControlMsg::SetPan(0.0));
                }
                KeyCode::Char('q') | KeyCode::Char('Q') => break,
                _ => {}
            }

            print!("\r  gain={:+.1} dB   pan={:+.2}    ", gain_db, pan);
            use std::io::Write;
            std::io::stdout().flush()?;
        }
    }

    disable_raw_mode()?;
    Ok(())
}

Experimentos pra fazer:

  1. Fader rápido. Pressione ↓ várias vezes rapidamente. Com smoothing (tau=20ms) o ganho deve seguir suave, sem clicks. Tire o smoothing temporariamente (tau=0) e repita — vai ouvir clicks.
  2. Mute dramático. Com áudio tocando alto, aperte M. Com smoothing normal, dá um fade-out rápido (mas audível). Pro uso real de "mute instantâneo", você quer a Abordagem 3 (snap detection) — escute a diferença.
  3. Pan estéreo. Use fones de ouvido. Aperte ← várias vezes. O som move pra esquerda gradualmente. Com a lei -3dB, o volume total fica constante durante o movimento. Tente trocar pra lei linear (-6dB) e compare — no centro, sinal fica mais baixo.
  4. Unity restore. Em qualquer posição, aperte U. Gain volta pra 0dB e pan pro centro, com smoothing suave. Observe como é satisfatório o movimento natural.

Glossário
ZIPPER NOISE
Artefato audível quando um parâmetro muda por passos muito pequenos e frequentes. Soa como um "zíper rasgando".
SMOOTHING
Técnica de interpolar valores de parâmetro gradualmente pra evitar zipper noise e clicks.
ONE-POLE FILTER
Filtro exponencial simples usado pra smoothing. Três operações por amostra.
TAU (τ)
Constante de tempo. Tempo em segundos pra um one-pole atingir ~63% do target.
dB (DECIBEL)
Unidade logarítmica de nível. dB = 20 · log10(amplitude). 0 dB = referência. -6 dB = metade da amplitude.
CURVA DE FADER
Mapeamento entre posição física (0-100% do curso) e ganho em dB. Unity tipicamente em 75% do curso.
UNITY
Ganho de 0 dB, ou seja, amplitude 1.0 (sem alteração). Marcado como "0" na escala do fader.
PAN LAW
Regra que define o ganho de cada canal (L/R) conforme a posição de pan. Padrão digital: -3 dB constant power.
CONSTANT POWER
Lei de pan onde a soma dos quadrados dos ganhos L e R é sempre 1. Resulta em volume percebido constante.
CHANNEL STRIP
Conjunto de processamento de um canal individual: gain, EQ, dinâmicas, pan. Tipicamente uma "coluna" na UI da mesa.
SNAP DETECTION
Técnica que detecta mudança grande no target e aplica transição diferente (snap ou cross-fade) em vez de smoothing normal.
VCA
Voltage-Controlled Amplifier. Em mesas digitais, mecanismo que permite um fader controlar proporcionalmente vários canais.
